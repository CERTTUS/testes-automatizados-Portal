## Tela / fluxo

Serviços › Ordens de Serviço › Alterar Ordem de Serviço → aba de dados → campo **Celular**.

## Comportamento atual

- O campo Celular só aceita 10 dígitos. Ao digitar `(46)99117-8665` (celular com o nono dígito), o último dígito é cortado e a OS é gravada com `4699117865`.
- Para gravar, o usuário só consegue informar no formato antigo `(46)9117-8665`.
- Com o celular trocado na alteração, o BackOffice atualiza o link do Portal com o número cortado: o link passa a aceitar `554699117865` e **recusa o número real do cliente** `5546991178665`. O cliente perde o acesso ao Portal.
- Causa no fonte: `Servicos/Retificas/RecepcaoServicos.SC2`, objeto `pgPageFrame.pgDados.edtCelular` com `InputMask = "(99)9999-9999"` e `MaxLength = 12`, sem tratamento para celular de 11 dígitos. A máscara foi definida no commit `c52f3e55` (02/09/2026, URG-8081); a PR #2278 não altera o campo, mas o fluxo da URG-11817 depende dele (troca de celular atualiza o link).

## Comportamento esperado

- O campo Celular aceita celular com 11 dígitos (`(99)99999-9999`) e continua aceitando 10 dígitos.
- A OS é gravada com o número completo digitado e a troca de celular atualiza o link do Portal para esse número (o mesmo link aceita o celular novo e recusa o anterior).

## Evidência

- OS 0001/027016 (banco local `portaldocliente`), alterada às 15:44 de 17/11/2026: `PCRTASE0.Celular = '4699117865'` após digitar `(46)99117-8665`.
- Microsserviço local: `POST /api/v1/servicos/portal/link` → 200 (telefone do link atualizado), nenhuma mensagem no Talk (comportamento correto da alteração).
- `CT-INT-02` (OS 027016): aceita `554699117865` (número cortado) e recusa `5546991178665` (número real).
- Reproduzir: Alterar Ordem de Serviço → digitar `(46)99117-8665` no campo Celular → o campo fica `(46)9911-7865`.
